# ADR 0003：以受控文档入库流水线替代双自治 Agent

- 状态：已接受
- 日期：2026-08-10

InterWise 不建设两个自由自治、互相对话的题库 Agent。应用内可维护题库采用一条可恢复的文档入库流水线：确定性程序负责文件安全、解析、分块、契约校验、作用域和状态流转；知识原子生成器只依据原文生成候选；质量监督器结合原文、规则结果和目标题库相似原子给出结构化机器结论；私有 owner 或公共题库管理员通过批次终审显式触发发布。

机器质量状态与人工审核状态必须分离。自动通过只表示候选可以进入批次终审，不能冒充人工接受；需要人工的异常项在终审前必须被处理；自动淘汰项默认不发布。终审先在 MySQL 中形成可审计草稿和发布状态，再通过可重试的索引步骤同步 Qdrant，任何模型节点都没有发布、跨 owner 读取或切换 Provider 的权限。

## 考虑过的方案

- 两个自治 Agent 互相生成和监督：拒绝。它会增加模型调用、状态恢复和调试复杂度，同一模型还可能重复强化错误。
- 保留现有单模型自检并增加批量接受：拒绝。旧自检没有读取完整原文或同作用域相似原子，且结果不构成正式质量门。
- 上传后自动发布：拒绝。它会绕过人工终审并直接污染面试检索。

## 后果

- 用户的常规操作从逐条机械接受收敛为“处理异常项 + 一次批次终审”。
- 主应用需要持久化生成调用检查点、已保存模型响应、机器审核结论、终审 revision 和最终原子列表。自动恢复不得重复调用结果不确定的模型请求；用户显式重试才授权再次调用，终审重试不得重复导入草稿。
- 私有知识库只允许 owner 发起流水线；公共 starter 知识库只允许 `ADMIN` 发起，普通用户只读。
- 公共题库只是发布目标。源文档、构建批次、候选和异步作业始终保持 `PRIVATE + 发起管理员 owner_user_id`，其他管理员也不能读取或重试；终审发布后的知识原子才写入 `PUBLIC + owner_user_id = null`。
- 公共目标的机器监督按 `PUBLIC + owner=null` 检索相似原子；MySQL 将其编译为 `owner_user_id IS NULL`，Qdrant 将其编译为 owner payload 为空，不能把 null 解释为“不限制 owner”。幂等键同时绑定发起用户、知识库、配置 ID、规范化 Provider、连接端点、模型、temperature、提示词版本、分类和文件哈希，但不包含 API Key，避免共享知识库或可编辑 Provider 配置造成旧批次复用。
