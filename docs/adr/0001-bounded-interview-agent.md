# ADR 0001：采用有边界的单轮面试 Agent

- 状态：已接受
- 日期：2026-08-04

## 背景

InterWise 原有面试链路由显式阶段状态机、动态 RAG 和固定 Prompt 驱动，稳定但“下一问为什么这样问”主要由手工规则决定。比赛版本需要让系统能根据候选人的最新回答，自主选择深挖、补救、换题、追问简历或进入 HR，同时不能牺牲岗位隔离、可解释性和失败可恢复性。

项目已经使用 LangChain4j 0.29.1。为了引入 Agent 而整体迁移到 Spring AI，会同时改动模型配置、流式输出和既有 RAG 链路，收益不足以覆盖比赛前的回归风险。

## 决策

1. 保留现有技术栈，在 LangChain4j 上实现 `InterviewOrchestrator`，每轮只产出一个 `InterviewTurnPlan`。
2. Agent 只在技术面阶段参与决策；开场、HR 和收尾继续使用稳定规则。
3. Agent 只能选择以下动作：`DEEPEN`、`REMEDIATE`、`SWITCH_TOPIC`、`PROBE_RESUME`、`MOVE_TO_HR`、`CONTINUE_PHASE`。
4. Agent 只能调用三个只读工具：
   - 当前用户、当前岗位范围内的知识检索；
   - 当前用户绑定到当前岗位的简历证据；
   - 当前用户、当前岗位的学习覆盖情况。
5. 工具的用户 ID、岗位 ID 和面试记录 ID 全部由服务端绑定，模型不能传入或改写这些作用域参数。
6. 单轮最多调用 3 次工具，规划设置超时；模型、工具、超时或 JSON 契约失败后，当前面试会话固定回退到稳定规则，后续轮次不反复尝试失败的 Agent。
7. Agent 必须返回严格 JSON。动作和工具证据必须真正进入下一问 Prompt 或阶段决策，不能只作为前端标签展示。
8. 数据库只保存动作、模式、工具名、证据原子 ID、安全摘要和稳定失败码，不保存思维链、Provider 原始错误、URL、Token 或密钥。
9. 前端通过 SSE 接收 `orchestration` 事件，只展示安全摘要、决策模式和友好的工具名称。

## 结果

优点：

- 比固定流程多了一层可验证的自主决策，同时保留原有状态机作为安全底座。
- RAG、简历和学习覆盖从孤立模块变成 Agent 可按需调用的教学证据。
- 每轮决策可观测、可回放，演示时能解释“为什么继续深挖或换题”。
- Agent 不可用时仍可完成整场面试。

代价：

- 技术面每轮最多增加一次规划模型调用，带来额外延迟和用户侧模型费用。
- Tool Calling 兼容性取决于用户配置的 OpenAI-compatible 模型；不兼容时只能回退稳定规则。
- 这不是开放式多 Agent 系统，也不允许模型任意创建工具、修改数据或跳过权限边界。

## 暂不采用

- 全量迁移 Spring AI：比赛前改动面过大，且不能直接提升产品闭环。
- 完全自治面试 Agent：难以保证阶段、题库作用域、成本和演示稳定性。
- 把题库维护开放给普通用户：比赛 Demo 先使用内置公共 starter 题库，内容由管理员维护。
