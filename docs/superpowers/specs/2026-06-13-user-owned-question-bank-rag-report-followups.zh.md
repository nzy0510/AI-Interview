# 用户自主管理题库与 RAG 报告后续优化

状态：待规划
日期：2026-06-13
关联设计：`docs/superpowers/specs/2026-06-13-user-owned-question-bank-rag-report-design.md`

## 说明

本文记录本轮需求澄清中有价值、但不进入第一版改造范围的事项。第一版应优先完成用户私有岗位、私有题库导入、统一 LLM 配置、RAG 面试约束、异步报告生成和旧结构迁移。

下列事项只有在第一版稳定、测试和部署路径清楚之后，再逐项提升为独立设计或开发计划。

## 1. 按任务路由多个 LLM Provider

暂缓原因：

- 第一版已经明确保持一个用户启用的 OpenAI-compatible Provider。
- 多 Provider 会增加配置理解成本、失败定位成本和账单不可控风险。
- 需要定义面试、导入、二审、报告、HR 评分等任务的路由规则。

后续可选方向：

- 支持按任务选择 Provider。
- 支持默认 Provider 加任务覆盖配置。
- 为每类任务展示预计成本、超时和失败记录。

触发条件：

- 用户明确需要低成本模型处理导入、高质量模型处理面试或报告。
- 单 Provider 难以兼顾响应速度、质量和成本。

## 2. 外部消息队列

暂缓原因：

- 第一版面向本地子部署和云端平台两种场景，外部 MQ 会增加自部署门槛。
- MySQL job 表加 Spring TaskExecutor 已能覆盖导入、索引和报告生成的 MVP 需求。

后续可选方向：

- 引入 Redis Stream、RabbitMQ 或其他队列。
- 将 report、import、embedding、review 分为不同队列。
- 支持多实例 worker 横向扩展。

触发条件：

- 云端并发用户明显增加。
- job 表轮询成为瓶颈。
- 需要更强的延迟控制、优先级或死信队列能力。

## 3. 对象存储

暂缓原因：

- 第一版可使用本地文件系统保存原始文件和转换后的 Markdown。
- 对象存储会引入额外部署配置和鉴权复杂度。

后续可选方向：

- 支持 S3-compatible 存储。
- 支持 MinIO 作为本地部署选项。
- 将原始文件、Markdown、导入日志和报告附件统一抽象为 blob。

触发条件：

- 云端部署需要多实例共享文件。
- 文件量增长导致本地磁盘管理困难。
- 需要文件生命周期策略或冷存储。

## 4. 一个岗位多个知识库

暂缓原因：

- 第一版已经确认一个岗位默认绑定一个知识库。
- 单知识库内部可以通过文件、标签、领域字段管理多个知识领域。

后续可选方向：

- 支持岗位下创建多个知识库。
- 面试前选择启用哪些知识库。
- 支持公共知识库和私有知识库组合。

触发条件：

- 用户需要同一岗位下严格隔离不同课程、公司、面试方向或难度层级。

## 5. 面试时标签筛选

暂缓原因：

- 第一版只做文件和知识原子的轻量标签，用于管理和浏览。
- 面试时引入标签筛选会增加题目覆盖度、追问策略和无命中处理的复杂度。

后续可选方向：

- 面试开始前选择标签范围。
- 支持标签权重。
- 支持岗位默认标签组合。

触发条件：

- 用户希望针对某个子领域做专项模拟面试。
- 私有题库规模扩大，单岗位内领域跨度较大。

## 6. 更多导入格式

第一版只支持：

- PDF
- DOCX
- Markdown / MD
- TXT

后续可选扩展：

- HTML
- PPTX
- XLSX
- ZIP 批量导入
- 网页 URL 抓取

触发条件：

- MarkItDown 在目标格式上转换质量可接受。
- 能清楚展示转换失败原因和可修复建议。
- 文件安全扫描和大小限制已经明确。

## 7. 更强的知识原子质量流水线

第一版采用 LLM 二审，但不做过度复杂的质量管理。

后续可选方向：

- 原子重复检测。
- 原子覆盖度评估。
- 难度分布分析。
- 按岗位能力模型自动补齐缺失知识点。
- 导入后生成质量报告。

触发条件：

- 用户导入大体量文档后，需要知道题库是否覆盖岗位核心能力。
- LLM 生成的原子质量波动影响面试质量。

## 8. 配额与平台限制

暂缓原因：

- 第一版先采用保守限制：单文件 20MB、单次导入最多 100 个知识原子。
- 更细的配额体系会影响云端商业化和自部署体验，需要单独设计。

后续可选方向：

- 按用户限制岗位数、文件数、总存储量、导入次数。
- 按管理员配置云端默认限制。
- 自部署模式允许关闭或放宽限制。

触发条件：

- 项目进入多人云端平台部署。
- 需要避免滥用上传、LLM 调用或 embedding 资源。

## 9. 团队与组织空间

暂缓原因：

- 第一版以个人私有岗位和管理员公共岗位为核心。
- 团队协作会引入空间、成员、角色和共享权限。

后续可选方向：

- 团队知识库。
- 团队岗位模板。
- 成员邀请和权限分级。
- 团队级 LLM Provider 或额度管理。

触发条件：

- 项目服务学校、班级、社团、公司或培训组织。

## 10. 公共模板市场与分享

暂缓原因：

- 第一版只保留内置公共岗位，并允许用户复制为个人岗位。
- 用户发布公共模板涉及审核、版权、质量和滥用治理。

后续可选方向：

- 用户将私有岗位发布为模板。
- 管理员审核后进入公共模板列表。
- 模板支持版本、评分和复制次数。

触发条件：

- 用户希望贡献题库。
- 平台需要社区化内容增长。

## 11. 高级报告分析

第一版报告关注每轮问答的综合得分、参考答案和改进建议。

后续可选方向：

- 多次面试趋势分析。
- 岗位能力雷达图。
- 知识点薄弱项聚合。
- 自动生成复习计划。
- 题库覆盖与用户薄弱项联动推荐。

触发条件：

- 用户积累了足够多的面试记录。
- 报告需要从单次反馈升级为长期学习闭环。

## 12. 部署 Profile

暂缓原因：

- 第一版仍然同时服务本地自部署和云端平台，但不额外抽象部署产品形态。

后续可选方向：

- `local` profile：本地文件系统、单实例、低依赖。
- `cloud` profile：对象存储、多实例 job worker、管理员运营功能。
- 明确不同 profile 的默认限制和安全策略。

触发条件：

- 云端部署进入长期运营。
- 自部署用户需要更低门槛的一键配置。

## 13. 开发者工具与旧管理入口清理

第一版会把旧结构迁移到新结构，但部分开发者工具可能仍需保留一段时间用于维护。

后续可选方向：

- 下线 `APP_ADMIN_TOKEN` 管理模式。
- 将旧 question-bank admin 页面彻底迁移到角色权限体系。
- 梳理脚本导入包生成流程和系统内导入流程的边界。

触发条件：

- 新导入流程稳定覆盖旧流程能力。
- 管理员可以在系统内完成公共题库维护。

## 14. 非 MVP 安全增强

第一版必须做到权限隔离、私有题库不可越权访问、API Key 不回显、文件类型和大小限制。

后续可选增强：

- 文件病毒扫描。
- 文档内容敏感信息检测。
- 导入任务审计日志。
- 管理员操作审计。
- Provider 调用成本和异常监控。

触发条件：

- 云端平台对外开放注册。
- 上传内容来源不可控。
- 管理员数量增加。

## 15. 提升为开发计划的标准

任一后续项进入开发前，应补齐：

- 明确用户故事。
- 数据模型变更。
- 接口 contract。
- 权限和隐私边界。
- 迁移策略。
- 前后端验证命令。
- 回滚或降级策略。
