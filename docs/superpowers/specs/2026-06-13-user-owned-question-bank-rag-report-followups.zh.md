# 用户自主管理题库与 RAG 报告后续优化

状态：按 2026-06-15 受控开放方向修订
日期：2026-06-13，修订：2026-06-15
关联设计：`docs/superpowers/specs/2026-06-13-user-owned-question-bank-rag-report-design.zh.md`
当前领域边界：`CONTEXT.md`

## 说明

本文记录有价值、但不进入当前第一版改造范围的事项。
第一版应优先完成：公共/私有岗位与题库作用域、本机 Agent + 题库维护 skill 生成导入包、将原管理员题库维护面板开放为用户私有题库工作台、人工审查发布、Qdrant 严格作用域检索、结构化面试快照、异步报告生成和旧流程收口。

当前方向是受控开放，不再把“应用内任意 PDF/DOCX/Markdown/TXT 上传后自动切分、自动生成高质量原子、自动发布”作为 MVP 主线。
下列事项只有在第一版稳定、测试和部署路径清楚之后，再逐项提升为独立设计或开发计划。

## 1. 应用内文档转换与 MarkItDown 服务

暂缓原因：

- 当前 MVP 的题库生产主路径已经转为本机 Agent + 题库维护 skill 生成结构化导入包，再通过原维护面板风格的工作台导入发布。
- 应用内文档转换会把产品重新推向完全开放的任意文档导入，质量和安全边界更难控。
- MarkItDown、文件存储、转换失败恢复、文件安全扫描都会增加自部署门槛。

后续可选方向：

- 将 PDF、DOCX、Markdown/MD、TXT 转换为导入包草稿，而不是直接发布原子。
- 使用独立 `document-converter` 服务，避免 Java 请求处理中启动 Python。
- 保存原始文件、转换后 Markdown、转换日志和用户可见失败原因。

触发条件：

- 受控导入包流程稳定，用户明确需要应用内辅助转换。
- 能清楚展示转换质量风险，并始终落到草稿审查流程。
- 文件安全、大小限制和清理策略已经明确。

## 2. 应用内 LLM 原子生成与二审

暂缓原因：

- 之前的应用内 LLM 批量生成质量较好但耗时长，结构化快路径速度快但质量不稳定。
- 当前路线把高质量原子生产放回本机 Agent + skill，主应用复用原题库维护面板流程承担授权、导入、审查和发布。
- 应用内自动生成容易让用户误以为任意文档都能自动变成可靠题库。

后续可选方向：

- 在导入包草稿基础上提供“辅助改写”“补全追问路径”“质量检查”按钮。
- 为单个原子提供 LLM 建议，而不是大批量自动生成。
- 允许管理员在公共 starter 维护中使用受控 LLM 审查，但仍需人工发布。

触发条件：

- 导入包 schema 和人工审查体验稳定。
- 有可重复的质量评测集证明应用内 LLM 辅助能提升质量。
- 成本、超时、失败脱敏和用户 Provider 要求已经产品化。

## 3. 导入包 schema 版本治理

暂缓原因：

- 第一版只需要固定一个可校验的 JSON 导入包格式。
- 过早引入复杂兼容层会放大实现和测试成本。

后续可选方向：

- 为导入包增加 semver、schema URL 和兼容矩阵。
- 提供 schema migration 工具，把旧导入包升级到新版本。
- 在前端导入前显示版本兼容性和字段变化摘要。

触发条件：

- 导入包格式发生不兼容变化。
- 多个 skill 或外部工具开始生成导入包。

## 4. 题库维护 skill 质量评测

暂缓原因：

- 第一版目标是恢复可用的本机导入包生成能力，而不是一次性解决所有质量评测。
- 评测指标需要结合真实面试 RAG 使用效果，不能只看 JSON 格式正确。

后续可选方向：

- 建立导入包 lint：字段完整性、重复原子、难度分布、标签一致性、追问路径完整性。
- 建立小型人工黄金集，对比不同提示词、模型和输入结构的原子质量。
- 为 skill 输出生成质量报告，帮助用户在导入前修正。

触发条件：

- 用户开始批量维护多个岗位。
- 导入包质量波动明显影响面试追问效果。

## 5. 按任务路由多个 LLM Provider

暂缓原因：

- 第一版仍保持一个用户启用的 OpenAI-compatible Provider。
- 多 Provider 会增加配置理解成本、失败定位成本和账单不可控风险。
- 当前题库生产主路径在本机 Agent + skill 中完成，主应用更不应急于引入导入任务模型路由。

后续可选方向：

- 支持面试、报告、Mentor、原子辅助改写分别选择 Provider。
- 支持默认 Provider 加任务覆盖配置。
- 为每类任务展示预计成本、超时和失败记录。

触发条件：

- 用户明确需要低成本模型处理辅助维护，高质量模型处理面试或报告。
- 单 Provider 难以兼顾响应速度、质量和成本。

## 6. 外部消息队列

暂缓原因：

- 第一版面向本地自部署和云端平台两种场景，外部 MQ 会增加自部署门槛。
- MySQL job 表加 Spring TaskExecutor 已能覆盖导入包处理、索引和报告生成的 MVP 需求。

后续可选方向：

- 引入 Redis Stream、RabbitMQ 或其他队列。
- 将 report、import、embedding、review 分为不同队列。
- 支持多实例 worker 横向扩展。

触发条件：

- 云端并发用户明显增加。
- job 表轮询成为瓶颈。
- 需要更强的延迟控制、优先级或死信队列能力。

## 7. 对象存储与导入附件管理

暂缓原因：

- 当前 MVP 不要求主应用保存原始 PDF/DOCX 文件。
- 结构化导入包可以作为主要输入，降低文件存储、鉴权和清理复杂度。

后续可选方向：

- 支持 S3-compatible 存储。
- 支持 MinIO 作为本地部署选项。
- 将导入包、原始文件、转换后 Markdown、导入日志和报告附件统一抽象为 blob。

触发条件：

- 应用内文档转换进入开发。
- 云端部署需要多实例共享文件。
- 文件量增长导致本地磁盘管理困难。

## 8. 一个岗位多个知识库

暂缓原因：

- 第一版确认一个岗位默认绑定一个知识库。
- 单知识库内部可以通过标签、领域字段和导入批次管理多个知识领域。

后续可选方向：

- 支持岗位下创建多个知识库。
- 面试前选择启用哪些知识库。
- 支持公共知识库和私有知识库组合。

触发条件：

- 用户需要同一岗位下严格隔离不同课程、公司、面试方向或难度层级。

## 9. 面试时标签筛选

暂缓原因：

- 第一版只做知识原子的轻量标签，用于管理和浏览。
- 面试时引入标签筛选会增加题目覆盖度、追问策略和无命中处理的复杂度。

后续可选方向：

- 面试开始前选择标签范围。
- 支持标签权重。
- 支持岗位默认标签组合。

触发条件：

- 用户希望针对某个子领域做专项模拟面试。
- 私有题库规模扩大，单岗位内领域跨度较大。

## 10. 更多导入包来源

第一版只要求导入结构化 JSON 包。

后续可选扩展：

- HTML 或网页 URL 抓取后生成导入包。
- PPTX、XLSX、ZIP 批量资料转导入包。
- 从 Git 仓库、课程目录或 Markdown 文档集生成导入包。
- 从旧版本导入包或第三方题库格式转换。

触发条件：

- 转换质量可接受。
- 能清楚展示转换失败原因和可修复建议。
- 所有结果仍然进入草稿审查和显式发布流程。

## 11. 更强的知识原子质量流水线

第一版采用人工审查和结构化校验，不做过度复杂的质量管理。

后续可选方向：

- 原子重复检测。
- 原子覆盖度评估。
- 难度分布分析。
- 按岗位能力模型自动提示缺失知识点。
- 导入后生成质量报告。

触发条件：

- 用户导入大体量题库后，需要知道题库是否覆盖岗位核心能力。
- 导入包生成质量波动影响面试质量。

## 12. 配额与平台限制

暂缓原因：

- 第一版先采用保守限制：单次导入包大小、单包原子数量、岗位数量和任务并发数量。
- 更细的配额体系会影响云端商业化和自部署体验，需要单独设计。

后续可选方向：

- 按用户限制岗位数、导入包数、总原子数、发布原子数、重建索引次数。
- 按管理员配置云端默认限制。
- 自部署模式允许关闭或放宽限制。

触发条件：

- 项目进入多人云端平台部署。
- 需要避免滥用导入、LLM 调用或 embedding 资源。

## 13. 团队与组织空间

暂缓原因：

- 第一版以个人私有岗位和管理员公共岗位为核心。
- 团队协作会引入空间、成员、角色和共享权限。

后续可选方向：

- 团队知识库。
- 团队岗位模板。
- 成员邀请和权限分级。
- 团队级 LLM Provider 或额度管理。

触发条件：

- 项目服务学校、班级、社团、公司或培训组织。

## 14. 公共模板市场与分享

暂缓原因：

- 第一版只保留内置公共岗位，并允许用户复制为个人岗位。
- 用户发布公共模板涉及审核、版权、质量和滥用治理。

后续可选方向：

- 用户将私有岗位发布为模板。
- 管理员审核后进入公共模板列表。
- 模板支持版本、评分和复制次数。

触发条件：

- 用户希望贡献题库。
- 平台需要社区化内容增长。

## 15. 高级报告分析

第一版报告关注每轮问答的综合得分、参考答案和改进建议。

后续可选方向：

- 多次面试趋势分析。
- 岗位能力雷达图。
- 知识点薄弱项聚合。
- 自动生成复习计划。
- 题库覆盖与用户薄弱项联动推荐。

触发条件：

- 用户积累了足够多的面试记录。
- 报告需要从单次反馈升级为长期学习闭环。

## 16. 部署 Profile

暂缓原因：

- 第一版仍然同时服务本地自部署和云端平台，但不额外抽象部署产品形态。

后续可选方向：

- `local` profile：本地文件系统、单实例、低依赖。
- `cloud` profile：对象存储、多实例 job worker、管理员运营功能。
- 明确不同 profile 的默认限制和安全策略。

触发条件：

- 云端部署进入长期运营。
- 自部署用户需要更低门槛的一键配置。

## 17. 开发者工具与旧管理入口清理

第一版会把旧结构迁移到新结构，但部分开发者工具可能仍需保留一段时间用于维护。

后续可选方向：

- 彻底下线 `APP_ADMIN_TOKEN` 管理模式。
- 将旧 question-bank admin 页面彻底迁移到角色权限体系。
- 将题库维护 skill、导入包 schema、面板导入发布流程做成稳定开发者文档。
- 提供导入包示例、schema lint 和本地 dry-run 命令。

触发条件：

- 新导入包流程稳定覆盖旧流程能力。
- 管理员可以在系统内完成公共题库维护。

## 18. 非 MVP 安全增强

第一版必须做到权限隔离、私有题库不可越权访问、API Key 不回显、导入包字段校验和无作用域检索禁止。

后续可选增强：

- 文件病毒扫描。
- 文档内容敏感信息检测。
- 导入任务审计日志。
- 管理员操作审计。
- Provider 调用成本和异常监控。
- 导入包恶意内容检测和提示词注入检测。

触发条件：

- 云端平台对外开放注册。
- 上传内容来源不可控。
- 管理员数量增加。

## 19. 提升为开发计划的标准

任一后续项进入开发前，应补齐：

- 明确用户故事。
- 数据模型变更。
- 接口 contract。
- 权限和隐私边界。
- 迁移策略。
- 前后端验证命令。
- 回滚或降级策略。
